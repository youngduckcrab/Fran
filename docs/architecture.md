# 구조

## 메시지 한 통이 지나가는 길

```
승윤(ko)                     서버                          Fran(es)
   │                          │                               │
   │ ─ send "오늘 어땠어?" ──▶ │                               │
   │                          │ messages 테이블에 원문 저장     │
   │ ◀── message (원문) ────── │ ──── message (원문) ─────────▶ │   ← 즉시. 기다리지 않는다
   │                          │                               │
   │                          │ 번역 큐에 넣음                  │
   │                          │   └ 직전 12개 + 이 메시지        │
   │                          │     → LLM 한 번 호출             │
   │                          │     → translations 테이블 저장   │
   │                          │                               │
   │ ◀ message_updated ────── │ ─ message_updated ──────────▶ │   ← 1~3초 뒤
```

핵심은 **원문 전달과 번역을 분리**한 것이다. 번역이 몇 초 걸리더라도 메시지 자체는 바로 도착하고,
번역문은 같은 말풍선에 나중에 채워진다. 번역이 실패해도 대화는 끊기지 않는다 — 원문이 그대로 남고,
말풍선에 "다시 시도" 버튼이 붙는다.

## 왜 이렇게 했나

**번역 provider는 갈아끼울 수 있다.**
프롬프트와 출력 스키마는 하나로 두고, 모델 호출만 `TranslationProvider` 인터페이스 뒤로
숨겼다. 무료(Gemini)로 쓰다가 품질이 아쉬우면 env 한 줄로 유료(Claude)로 옮길 수 있고,
그때 프롬프트를 다시 쓸 필요가 없다.

**번역은 한 메시지당 API 호출 한 번.**
필요한 언어가 두 개든 네 개든 한 번의 호출에서 전부 받는다. 같은 맥락을 여러 번 보내지 않으니
싸고, 언어끼리 해석이 어긋나지도 않는다.

**번역 큐는 직렬.**
맥락을 읽는 번역이라 앞 메시지가 먼저 정리돼 있어야 한다. 사용자가 둘뿐이라 병렬화할 이유도 없다.

**원문은 불변.**
`messages.source_text` 는 한 번 쓰이면 절대 바뀌지 않는다. 번역은 전부 `translations` 테이블의
파생 데이터라, 모델을 바꾸거나 용어집을 고친 뒤 통째로 다시 돌려도 대화 기록은 멀쩡하다.

**번역 결과는 캐시가 아니라 저장.**
한 번 번역한 메시지는 다시 번역하지 않는다. 대화를 다시 열어도 API 비용이 들지 않는다.
다시 번역하고 싶으면 `retranslate` 이벤트로 명시적으로 요청한다.

**로그인 토큰은 사람마다 따로 저장한다.**
`localStorage` 는 같은 주소의 모든 탭이 공유한다. 키를 하나로 두면 한 브라우저에서 두
사람이 각자의 주소로 들어갈 때 나중에 로그인한 쪽이 상대의 토큰을 덮어써서, 두 탭 모두
같은 사람으로 로그인된다. `fran.token.<userId>` 로 나눠 저장하고, 탭이 열릴 때 주소의
`?u=` 로 자기 토큰을 고른다. `?u=` 가 없으면 마지막으로 로그인했던 사람을 쓴다.

**화면 문구는 사람마다 다르다.**
번역만 해주고 화면은 한 언어로 두면 한쪽은 앱 자체를 못 쓴다. 화면 언어는 그 사람의
"받아볼 언어" 첫 번째를 따라가고, 로그인 전에는 주소의 `?u=` 나 브라우저 설정으로 정한다.
서버가 내려주는 실패 사유도 문구가 아니라 코드(`translationErrorCode`)로 보내서 화면에서
각자의 언어로 푼다. 서버 문구를 그대로 띄우면 결국 한쪽은 못 읽는다.

**설치 매니페스트는 사람마다 만들어 준다.**
PWA 매니페스트를 정적 파일로 두면 두 사람의 폰에 같은 이름·같은 시작 주소의 앱이 깔린다.
서버가 `/manifest.webmanifest?u=<아이디>` 로 그때그때 만들고(`start_url` 은 그 사람의 `?u=`
주소, 이름은 **상대의 이름**, `lang` 은 그 사람의 화면 언어), 화면 쪽은 `<link rel="manifest">`
의 주소를 자기 것으로 바꿔 둔다. 아이콘에 자기 이름이 적혀 있는 것보다 상대 이름이 적혀
있는 편이 메신저답다. iOS 는 홈 화면 이름을 문서 제목에서도 가져가므로 `document.title` 도
상대 이름으로 맞춘다.

**보낸 사람에게는 번역문도 보여준다.**
번역을 거쳐 말하는 사이에서 정작 안 보이는 건 "내 말이 저쪽에 어떻게 도착했나"다.
내 말풍선에는 상대가 읽는 언어의 번역을 같이 띄우고, 기본값은 펼침이다 — 서로의 언어를
배우는 게 이 앱의 이유라서. 다만 접을 수는 있어야 한다. 접고 펴는 상태는 말풍선마다가
아니라 사람마다 하나로 두고 `localStorage` 에 남긴다. 말풍선마다 따로 기억하면 새 메시지가
올 때마다 다시 접어야 하고, 그러면 "안 보고 싶다"는 뜻을 앱이 계속 못 알아듣는 셈이 된다.
받는 쪽 화면에는 뜨지 않는다. 그쪽에는 이미 자기 언어로 도착해 있다.

**소리는 폰에 있는 것으로 낸다.**
발음을 들려주려고 TTS API 를 부르면 글자마다 돈이 들고 키도 하나 더 관리해야 한다.
브라우저의 음성 합성(`speechSynthesis`)은 공짜에 오프라인이고 이미 폰에 깔려 있다.
읽어주는 대상은 **내 언어가 아닌 쪽**이다. 상대가 보낸 말은 원문을, 내가 보낸 말은 상대에게
간 번역문을 읽는다 — 내가 쓴 내 말을 다시 들을 일은 없다.
목소리는 지역까지 골라서 스페인어는 칠레·중남미를 먼저 찾는다. 같은 스페인어라도 억양이
달라서, 배우는 쪽에는 실제로 듣게 될 발음이 맞다. 목소리 목록은 늦게 채워지므로 미리 받아
두고, iOS 는 사용자가 누른 그 순간에 `speak()` 가 불려야 소리를 내주므로 기다리지 않는다.
없는 언어면 조용히 마는 대신 그 자리에 "이 기기에 … 목소리가 없어요"라고 적는다.

**파일은 HTTP 로, 메시지는 WebSocket 으로.**
사진을 소켓에 실어 보내면 그동안 다른 메시지가 전부 그 뒤에 줄을 선다. 첨부는 먼저
`POST /api/attachments` 로 올려 두고, 보낼 때는 그 id 만 실어 보낸다. 보내는 순간에
서버가 "올린 사람이 같고 아직 어느 메시지에도 붙지 않았는지"를 확인하고 붙인다 —
남의 첨부 id 를 적어 보내서 남의 사진을 자기 메시지로 만드는 일을 막는다.
고르기만 하고 보내지 않은 첨부는 시작할 때 치운다.

**첨부도 Postgres 에 넣는다.**
파일을 디스크에 두면 무료 호스팅에서는 재배포마다 사라진다. 객체 저장소를 붙이면 계정이
하나 더 늘고 키를 또 관리해야 한다. 대화가 이미 Postgres 에 있으니 사진·음성도 같은 곳에
둔다. 대신 **올리기 전에 화면에서 줄인다**(긴 변 1600px, JPEG). 폰 사진을 원본으로 쌓으면
무료 DB 용량(0.5GB 정도)은 금방 찬다. 목록을 그릴 때는 바이트를 읽지 않고 설명만 읽는다.

**알림은 번역이 끝난 뒤에, 그리고 "보고 있지 않을 때".**
받자마자 보내면 상대는 자기가 못 읽는 언어로 된 알림을 받는다. 번역 파이프라인 끝에서
받는 사람이 읽는 언어로 적어 보낸다. "연결돼 있다"와 "보고 있다"는 다르다. 홈 화면에 두고
다른 앱을 보는 동안에도 연결은 한동안 살아 있어서, 연결만 보고 알림을 접으면 아무도 모른다.
화면 쪽에서 `visibilitychange` 를 서버에 알려 주고(`attention`), 보고 있는 사람에게만 접는다.
보고 있지만 채팅 밖에 있는 경우에는 앱 안에서 한 줄로 알린다 — 그래야 두 번 울리지 않는다.
서비스 워커는 조건을 따지지 않고 받은 알림을 그대로 띄운다. "받은 알림은 반드시 띄워야
한다"는 웹 푸시 규칙과 부딪히지 않으려면 접는 판단은 서버에서 끝내야 한다.
서명 키(VAPID)는 처음 한 번 만들어 DB 에 넣는다. 환경변수로 받으면 사람이 손으로 만들어
넣어야 하고, 재배포마다 새로 만들면 이미 등록된 기기의 알림이 전부 무효가 된다.

**음성은 글로 옮긴 다음 번역한다.**
받아쓴 글이 곧 그 메시지의 원문이 된다. 사람이 타이핑한 글이 없을 뿐, 번역·설명·알림·
미리보기가 모두 같은 자리를 본다(`messageText()`). 폰이 만드는 형식(webm/mp4)은 모델이
받지 않아서 ffmpeg 으로 ogg/opus 16kHz 모노로 바꿔 보낸다 — 말소리만 있으면 되니 올려
보낼 양도 같이 준다. ffmpeg 이 없는 곳에서는 컨테이너 이름만 바꿔 시도하고, 실패하면
받아쓰기만 실패로 남는다(소리는 그대로 들을 수 있다).
들린 언어가 보낸 사람의 모국어와 다르면 그 언어를 원문 언어로 삼는다. 공부 삼아 상대의
언어로 말해 보는 일이 이 앱에서는 흔하다.

**보관함은 대화 밖의 문장도 받는다.**
단어장 예문처럼 메시지가 없는 문장도 담을 수 있어야 해서 `message_id` 를 비워 둘 수 있게
했다. 대신 어디서 왔는지는 남긴다 — 예문이면 그 단어를. 보관함에서 문장만 덩그러니 있으면
왜 담았는지 잊는다. 이미 담았는지는 문장 자체로 견준다(대소문자·문장부호 차이는 무시).
메시지 id 로 견줄 수 없는 문장이 섞이기 때문이다.

**저장한 문장은 가리키지 않고 베껴 둔다.**
메시지 id 만 저장해 두면 번역을 다시 돌렸을 때 저장해 둔 문장이 슬그머니 바뀐다.
"이 표현 좋다" 싶어 담아 둔 문장이 사라지는 셈이다. 저장 시점의 문장과 그 짝을 함께 적는다.

**단어장 표제어는 기호를 뗀다.**
설명은 문장을 조각으로 잘라 주기 때문에 조각 끝에 `¿` `?` `,` 가 붙어 온다. 그대로 담으면
`¿Dormiste`, `Dormiste`, `dormiste?` 가 서로 다른 줄이 된다. 담을 때 문장부호를 떼고,
(사람, 언어, 소문자 표제어)로 유일하게 두어 같은 단어를 또 담으면 뜻만 갱신한다.

**단어 하나만 묻는 길을 따로 둔다.**
모르는 단어가 하나 걸렸을 뿐인데 문장 전체 설명(`explain`)을 기다릴 이유가 없다. 문장 설명은
조각·문법 포인트·답장 예시까지 만들어 오느라 느리고 토큰도 많이 쓴다. 단어 하나짜리 풀이는
그 문장과 그 단어만 보내고 사전형·품사·뜻·이 문장에서의 쓰임만 받아 온다. 문맥(앞의 대화)은
보내지 않는다 — 단어의 뜻을 가르는 데는 그 문장이면 충분하다.
`(메시지, 문장 언어, 설명 언어, 단어)` 로 캐시한다. 읽다가 걸릴 때마다 누르는 일이라 금방
쌓이는데, 같은 문장의 같은 단어는 답이 달라질 이유가 없다. 문장이 열쇠에 들어 있으므로
문장에 없는 말이 오면 거절한다 — 캐시가 어긋나고, 물어볼 이유도 없다.

**문장을 자르는 일은 화면에서 한다.**
어디까지가 한 단어인지는 브라우저의 `Intl.Segmenter` 가 안다. 서버에서 잘라 내려보내면
중국어처럼 띄어쓰기가 없는 언어를 우리가 직접 갈라야 하는데, 그건 이미 브라우저가 하는 일이다.
자른 조각을 이어 붙이면 원래 문장이 그대로 나와야 한다 — 화면의 글이 원문과 달라지면 읽는
사람이 헷갈리고, 서버의 "이 문장에 있는 말인지" 확인도 어긋난다. `Intl.Segmenter` 가 없는
낡은 브라우저에서는 글자·숫자가 이어진 덩어리를 단어로 본다(중국어는 통째로 한 덩어리가
되지만, 안 되는 것보다는 낫다).

**"보고 있다"는 말에는 유효기간이 있다.**
앱을 보고 있는 사람에게는 폰 알림을 보내지 않는다 — 화면 안에서 알리므로 두 번 울릴
이유가 없다. 그런데 폰이 잠기거나 지하철에 들어가면 "이제 안 봐요"라고 말할 새도 없이
멈추고, TCP 는 상대가 사라져도 한참 동안 알려주지 않는다. 그 사이 연결은 멀쩡해 보이고
알림은 계속 걸린다 — 메시지가 와도 아무 일도 일어나지 않는 상태가 이어진다.
그래서 보고 있는 동안 앱이 15초마다 다시 알려 주고, 서버는 45초 넘게 소식이 없으면 더는
보고 있지 않다고 본다. 여기에 더해 20초마다 연결을 찔러 보고(ping) 답이 없으면 끊는다.
접속 표시도 같은 것을 보므로, 상대가 "접속 중"으로 남아 있는 유령도 함께 사라진다.

**알림을 보냈는지는 DB 에 적는다.**
메모리에 들고 있었더니 번역 도중 서버가 꺼진 메시지는 영영 알림이 가지 않았다. 한 줄만
바뀌는 UPDATE(`notified_at IS NULL`)로 찍으면, 여러 곳에서 동시에 불러도 한 번만 통과하고
서버가 다시 켜져 번역을 마칠 때 보낸다. 다시 번역을 돌릴 때 알림이 또 가지 않는 것도
같은 표시가 막아 준다.

**알림은 번역을 기다리되, 오래 기다리지는 않는다.**
못 읽는 언어로 된 알림은 알림이 아니므로 번역을 기다린다. 하지만 모델이 붐비면 그 기다림이
끝나지 않을 수도 있고, 그동안 상대는 메시지가 온 줄도 모른다. 8초가 지나면 있는 그대로
보낸다 — 늦게 제대로 아는 것보다 지금 대충 아는 편이 낫다. 보내는 쪽은 둘 중 먼저 닿는
쪽이고, 위의 한 번만 통과하는 표시가 중복을 막는다.

**옛 대화는 찾아 올라갈 때 가져온다.**
대화를 열 때 주는 것은 마지막 50통이다. 몇 달치를 미리 내려받으면 열 때마다 느려지고
대개는 보지도 않는다. 맨 위 가까이 올라가면 그보다 오래된 50통을 더 가져와 붙인다.
달라고 한 만큼 오지 않으면 그 위로는 없다는 뜻이라, 개수를 따로 세어 두지 않아도 된다.

붙이기 직전의 `scrollHeight` 와 `scrollTop` 을 적어 두었다가, 붙은 뒤에 늘어난 높이만큼
내린다. 안 그러면 보고 있던 말풍선이 화면 밖으로 밀려나 어디를 읽고 있었는지 잃는다.
사진과 음성은 한 박자 늦게 자리를 잡으므로 다음 프레임에 한 번 더 맞춘다.
맨 아래로 따라 내려가는 것은 **맨 아래를 보고 있을 때와 내가 보낸 말일 때만** 한다 —
옛 대화를 읽는 중에 새 메시지가 왔다고 끌어내리면 읽던 자리를 잃는다.

끊겼다 이어지면 hello 가 마지막 50통을 다시 준다. 그때 화면을 통째로 갈아 끼우면 위로
올려서 불러둔 옛 대화가 사라진다. hello 가 준 것만 갈아 끼우고 그보다 오래된 것은 둔다.

**찾기는 세 군데를 함께 본다.**
원문만 뒤지면 반쪽이다. 한국어로 친 말을 스페인어로 기억하고 있을 수도 있고, 음성
메시지는 아예 받아쓴 글에만 있다. 원문·번역문·받아쓴 글을 한 질의로 본다(`EXISTS`
두 개를 붙인다 — JOIN 으로 펼치면 번역 수만큼 같은 메시지가 겹쳐 나온다).
찾은 말이 들어 있는 쪽을 골라 보여준다 — 스페인어로 쳤는데 한국어 원문이 뜨면 "이게 그건가"
싶다. `%`, `_` 는 글자 그대로 찾는다(LIKE 의 특수문자다).

**악센트는 확장 없이 뗀다.**
`extrano` 로 쳐도 `extraño` 가 찾혀야 한다. 한국어 자판으로는 `ñ` 를 칠 수조차 없다.
`unaccent` 확장을 쓰면 한 줄이지만 확장을 깔 수 있는지가 호스팅마다 다르다. NFD 로
풀어헤치면 악센트가 뒤에 딸린 부호로 떨어져 나오므로, 그 부호(U+0300~U+036F)만 지우면
된다 — 기본 기능만으로 된다. 한글과 한자는 이 구간에 걸리는 것이 없어 그대로 지나간다.
찾는 쪽과 찾히는 쪽에 똑같이 씌운다.

화면의 강조는 **원문 글자**에 걸려야 한다. 민짜끼리 견주면 자리가 어긋나는데, `ñ` 를 풀면
두 글자가 되기 때문이다. 민짜 글자마다 원래 몇 번째에서 나왔는지를 함께 들고 있다가
되짚는다(`web/src/search.ts`).

2만 통에 번역 2만 건을 쌓아 두고 재면 악센트를 떼기 전 10~22ms, 뗀 뒤 23~50ms 다.
둘이 쓰는 앱에서 이 차이로 무엇을 아끼자고 길을 둘로 나눌 이유는 없어서 한 길로 간다.
여기서 더 커지면 `pg_trgm` GIN 인덱스가 다음 수순이다.

**저장해 둔 것에서 대화로 돌아갈 수 있어야 한다.**
보관함의 카드만 보면 그 말이 어떤 얘기 끝에 나왔는지, 언제 한 말인지 알 수 없다.
저장한 문장·단어·사진은 모두 어느 메시지에서 왔는지(`messageId`) 들고 있으므로, 그
자리로 데려다 줄 수 있다.
**거슬러 올라가지 않고 그 자리만 잘라 온다.**
처음에는 나올 때까지 옛 대화를 끌어오게 했다. 쌓인 양에 비례해 느려지고, 어느 선을 넘으면
아예 못 찾는다. 대화는 계속 쌓이기만 하므로 그 선은 언젠가 반드시 넘는다.
서버가 그 메시지 둘레(앞뒤 25통)를 잘라 주면 한 번이면 끝난다 — 2만 통이든 20만 통이든
같다. 자리를 가를 때 시각만 보면 같은 순간에 온 두 통을 못 가르므로, 목록을 그리는
순서와 같은 `(created_at, id)` 로 자른다.

**과거 한 토막을 보는 동안은 실시간이 아니다.**
잘라 온 토막 아래에 새 메시지를 붙이면 사이가 뚝 끊긴 목록이 된다. 끝(`atTail`)을 보고
있지 않으면 붙이지 않고, 적어 두지도 않는다(다음에 열었을 때 그 토막이 뜨면 곤란하다).
hello 도 마찬가지로 건드리지 않는다. 아래로 내려와 끝에 닿거나 "최근 대화로" 를 누르면
그때 다시 실시간이 된다.

**아래로 이어 붙일 때는 끌어내리지 않는다.**
붙이자마자 맨 아래로 끌어내리면 다시 바닥에 닿아서 또 받아오고, 그 꼬리를 물어 끝까지
달려간다(처음 만들었을 때 한 번에 195번을 물어봤다). 사람이 실제로 내려온 만큼만 붙는다.
"최근 대화로" 를 누르는 순간 받아오던 것이 늦게 도착하면 최신 목록 뒤에 옛 토막이 다시
붙으므로, 번호를 매겨 두고 달라졌으면 버린다.

찾아가는 동안에는 "맨 아래로" 를 멈춘다. 애써 찾아 놓고 맨 아래로 끌려가면 아무 일도 안
한 것이 된다. 도착하면 가운데에 놓고 잠깐 둘레를 밝힌다 — 화면 한가운데에 놓아도 어느
것인지 눈에 바로 들어오지는 않는다.

**보관함은 한 군데서 받아 나눠 준다.**
저장한 문장·단어장·사진첩을 화면마다 따로 받아왔다. 홈에서 숫자를 세려고 한 번, 단어장을
열면서 또 한 번. 같은 것을 두 번 받는 데다, 화면을 열 때마다 빈 목록이 잠깐 보였다.
`Shell` 이 한 번 받아 아래로 내려주고, 화면들은 그린 것만 한다. 받은 것은 대화와 같이
이 기기에 적어 두므로 다음에 열면 기다릴 것이 없다.
한쪽에서 지우면 다른 쪽에도 바로 반영된다 — 목록이 하나뿐이기 때문이다.

**같은 목록을 화면으로도 시트로도 쓴다.**
채팅을 보면서 보관함을 열 수 있어야 하는데, 그렇다고 목록을 두 벌 만들 이유는 없다.
목록 컴포넌트에서 머리말(뒤로가기 + 제목)만 조건부로 떼어냈다. `onBack` 이 있으면 한
화면으로, 없으면 시트 안에 들어가는 알맹이로 쓴다. 언어 고르기·외움 표시·예문·지우기가
어느 쪽에서든 똑같이 동작하는 것은 같은 코드이기 때문이다.

**다시 들어왔을 때 빈 화면을 보여주지 않는다.**
앱을 열면 서버에 연결해 hello 를 받아야 대화가 보인다. 무료 호스팅의 서버는 한동안 쓰지
않으면 잠들고 깨어나는 데 30초쯤 걸리는데, 그동안 화면이 비어 있으면 사람은 앱이 멈춘
줄 안다. 마지막으로 본 대화(50통)를 이 기기에 적어 두고 열자마자 그걸 그린다. hello 가
오면 통째로 덮인다. 서버가 원본이고, 적어 둔 것은 "보여줄 것이 아무것도 없는 순간"만
메운다. 로그아웃하면 지운다.

**돌아온 순간에는 기다리던 타이머를 버린다.**
연결이 끊기면 재시도 간격이 점점 늘어난다. 그런데 사람이 앱을 다시 여는 순간은 그 간격
어디쯤인지와 아무 상관이 없다. 그때가 가장 급한 때인데도 다음 시도까지 몇 초를 더
기다리게 된다. 화면이 다시 보이거나(visibilitychange·focus) 네트워크가 돌아오면
(online) 타이머를 버리고 지금 시도한다. 실패해서 버리는 요청 하나가 사람을 빈 화면 앞에
세워 두는 것보다 훨씬 싸다. 같은 이유로 대기 시간의 상한도 15초에서 5초로 줄였다.

**같은 줄을 여러 번 읽지 않는다.**
프로필 하나를 만드는 데 user_settings 의 같은 줄을 다섯 번 읽고 있었다(주 언어, 표시 언어,
배경, 색, 성별·사는 곳). 접속할 때마다 두 사람 것이니 열 번이었다. 로컬 DB 에서는 티가
안 나지만 멀리 있는 DB 에서는 그대로 기다리는 시간이 되고 연결 풀도 그만큼 잡아먹는다.
한 번 읽어서 나눠 쓴다 — 접속 한 번의 질의가 16건에서 8건으로 줄었다.

**고친 글은 원문 자리를 덮고, 번역은 그 자리에서 비운다.**
보낸 글을 고치면 옛 번역은 그 순간부터 틀린 말이다. 새 번역을 기다렸다 한꺼번에 바꾸면
그 몇 초 사이에 상대가 어긋난 말을 읽는다. 그래서 고치는 즉시 번역을 비우고 "번역하는 중"
으로 되돌린 뒤에 다시 돌린다. 고쳤다는 사실은 숨기지 않는다(`editedAt`) — 상대가 아까 읽은
말과 다르다는 걸 알아야 한다.
고침은 보낸 사람만, 글이 실제로 달라졌을 때만 통과한다(`WHERE sender_id = $ AND source_text <> $`).
같은 글로 다시 저장하면 SQL 이 아무 줄도 건드리지 않으므로 번역도 돌지 않는다.
알림은 보내지 않는다. 새로 온 말이 아니라 이미 읽은 말이 바뀐 것이라, 폰을 울릴 일이 아니다.

**엔터는 줄바꿈이다.**
데스크톱 메신저의 관습(엔터로 보내기)을 폰에 그대로 가져오면, 문단을 나누려다 반쯤 쓴
말이 날아간다. 보내는 일은 버튼 하나로 충분하고, 잘못 눌러 잃는 것이 훨씬 크다.
대신 입력칸이 줄 수에 맞춰 늘어나야 한다 — 한 줄만 보이면 쓴 것을 다시 읽을 수가 없다.

**무엇을 크게 볼지는 기기에 남긴다.**
번역만 / 원문+번역 / 원문만은 취향이 아니라 그날의 상태다(공부하는 날, 바쁜 날). 서버에
두면 폰과 컴퓨터가 같이 움직여야 하는데 그럴 이유가 없다. localStorage 에 두고, 예전의
"원문 항상 보기" 켬/끔도 한 번은 읽어서 골라 둔 것을 잃지 않는다.
어느 쪽을 골라도 말풍선을 누르면 나머지가 나온다 — 모드는 기본값을 정할 뿐, 가리는 것이
아니다. 음성의 받아쓴 글만은 어느 모드에서든 보인다. 뭐라고 말했는지가 가장 배울 거리가
많은 부분이라서.

**번역은 두 사람이 누구인지 안다.**
스페인어는 자기 얘기를 할 때도("cansado/cansada") 상대를 부를 때도 성에 따라 말이 달라지는데,
한국어에는 그 단서가 없다. 모르면 모델이 기본값(대개 남성형)으로 찍는다. 사는 곳도 마찬가지다 —
칠레 사람에게 `vosotros` 나 `vale` 가 가면 곤란하다. 그래서 성과 사는 곳을 프로필에 두고
시스템 프롬프트의 "두 사람" 소개에 함께 싣는다.
`.env` 가 기본값이고 앱의 설정이 그것을 덮는다. 두 사람짜리 앱이라 한쪽(서버를 쥔 사람)이
둘 다 정해 두는 길과, 각자 자기 것을 고치는 길이 둘 다 필요하다.
모를 때 찍지 않는 것이 중요해서, 성이 적히지 않았으면 성이 드러나지 않게 돌려 쓰라고 못박는다.

**소리로 넘기기 전에 이모지를 걷어낸다.**
음성 합성기는 이모지를 이름으로 읽는다("빨간 하트"). 발음이 궁금해서 누른 사람에게는
없느니만 못한 말이다. 지운 자리는 공백으로 둔다 — "좋아❤️사랑해" 를 붙여 버리면 없던 한
단어가 된다. `ㅋㅋ` 같은 낱자 나열도 함께 지운다. 한국어 대화에서는 그게 곧 이모티콘인데,
합성기는 낱자 이름("키읔")을 읽으려 들어서 웃음소리가 되지 않는다.
읽을 글자가 하나도 남지 않으면 버튼 자체를 띄우지 않는다(`hasSpeech`). 눌러도 아무 일
없는 버튼은 고장 난 것처럼 보인다.

**단어장에는 사전형으로 담는다.**
`fui` 를 그대로 담아 두면 다음에 `fue` 를 만났을 때 같은 단어인 줄 모른다. 표제어는 `ir` 로
담고, 이 문장에서 어떻게 쓰였는지는 메모로 붙인다 — 왜 담았는지가 남아야 나중에 알아본다.

**뒤로가기는 기록을 밀어 넣어 받는다.**
홈 화면에 설치한 웹앱은 방문 기록이 하나뿐이라, 뒤로가기를 누르면 앱이 그대로 꺼진다.
화면이나 창이 열릴 때 기록을 한 칸 밀어 넣고, 뒤로가기가 오면 맨 위에 열린 것을 닫는다.
밀어 넣고 빼는 일은 한 박자 미뤄서 한다 — 메뉴를 닫으면서 다른 창을 여는 순간에 그때그때
건드리면, 방금 연 창의 기록 칸을 도로 지워 버린다(`backstack.ts`).

**테마는 색 두 개로 정한다.**
배경·면·테두리·강조색은 그 둘에서 섞어 만든다(`color-mix`). 테마마다 스무 줄씩 늘어놓으면
하나만 고쳐도 다른 테마가 어긋난다. 설정의 동그라미에도 같은 값을 걸어 두어, 고르기 전에
무슨 색인지 그대로 보인다.

**그림은 이모지 대신 선 그림으로.**
🖼 🎤 ⭐ 같은 이모지는 기기마다 다른 그림이 나오고 색과 두께가 제각각이라 앱 안에서 겉돈다.
같은 굵기·같은 둥근 끝으로 그린 SVG 는 글자 색을 그대로 따라가고 어느 기기에서나 같아
보인다(`Icon.tsx`). 반응 이모지만 예외다 — 그건 꾸밈이 아니라 내용이다.

**알림을 눌렀을 때는 띄우는 것이 먼저다.**
창 손잡이(`WindowClient`)에 `navigate()` 를 먼저 부르면 그 손잡이가 갈려서, 뒤이은 `focus()`
가 아무 일도 하지 않는다. 눌러도 앱이 안 열리던 이유였다. 순서를 뒤집고(띄우기 → 필요하면
이동), 어느 단계가 실패하든 마지막에는 새 창이라도 열도록 했다. 이미 그 사람의 창이 열려
있으면 새로 고치는 대신 `postMessage` 로 "채팅 열어" 라고만 알린다 — 새로 고치면 읽던
자리도, 쓰다 만 글도 날아간다.

**사진은 링크가 아니라 앱 안에서 연다.**
말풍선의 사진을 새 창을 여는 링크로 두었더니, 홈 화면에 설치한 앱에서는 그 창이 제대로
열리지 않고 앱이 처음 화면으로 돌아가 버렸다. 설치형 앱에는 "새 창"이 없다고 보는 편이 맞다.
크게 보기는 앱 안의 창으로 열고, 채팅과 사진첩이 같은 것을 쓴다.

**저장할 문장은 앱이 고르지 않는다.**
한 메시지에는 원문과 번역문이 함께 있다. 공부하려는 사람은 상대 언어 쪽을, 뜻만 남기려는
사람은 자기 언어 쪽을 담고 싶다. 자동으로 고르면 절반은 틀린다. 목록을 띄우고 고르게 한다.

**읽음은 메시지마다가 아니라 사람마다 한 줄.**
"누가 어디까지 읽었는지"를 시각 하나로 적는다(`read_state`). 메시지마다 읽음을 남기면 줄이
대화 길이만큼 늘어나는데, 둘이 쓰는 앱에서 필요한 건 "여기까지"뿐이다. 읽은 자리는 뒤로
가지 않는다 — 지난 대화를 보려고 위로 올라갔다 내려온 것뿐인데 읽음이 사라지면 곤란하다.
안 읽은 개수도 여기서 나온다. 화면에서 세던 때는 앱을 껐다 켜면 숫자가 사라지고, 폰과
컴퓨터가 서로 다르게 셌다.

**쌓인 알림도 읽은 그 순간에 치운다.**
앱을 여는 것만으로 치우면, 홈에서 단어장만 보다 나간 경우에도 알림이 사라져서 "봤다"는
표시만 없어지고 메시지는 안 읽은 채로 남는다. 읽음을 적는 바로 그 자리에서 함께 치운다.

**읽었다고 치는 순간은 "보고 있을 때".**
채팅 화면이 떠 있어도 탭이 가려져 있으면(다른 앱을 보는 중) 읽은 것이 아니다.
`visibilitychange` 를 같이 본다. 알림만 받은 것도 읽은 것이 아니다.

**반응은 사람당 하나.**
여러 개를 달 수 있게 하면 누가 뭘 달았는지 세는 화면이 필요해진다. 둘이 쓰는 앱에서는
(메시지, 사람)을 기본키로 두고 새로 누르면 바꾸는 편이 단순하고, 같은 걸 다시 누르면
지워지는 것도 자연스럽다.

**말풍선의 손가락 동작은 한곳에서 다룬다.**
길게 누르기와 옆으로 밀기가 같은 pointerdown 에서 갈린다. 따로 만들면 서로의 타이머를
못 보고 둘 다 걸리거나 둘 다 안 걸린다. 세로로 먼저 움직이면 스크롤이므로 둘 다 접는다
(`useBubbleGestures`). 가로만 우리가 쓰겠다는 뜻으로 말풍선에 `touch-action: pan-y` 를 준다.

**예문은 쌓이고, 겹치지 않는다.**
볼 때마다 새로 만들면 무료 한도를 갉아먹고 문장이 매번 바뀌어 외울 수가 없다. 만든 것은
저장하고, 더 보고 싶을 때만 하나씩 더 만든다 — 앞의 것을 갈아치우지 않는다. 같은 단어가
여러 상황에서 어떻게 쓰이는지가 배울 거리이기 때문이다.
겹치는 것은 두 겹으로 막는다. 이미 있는 문장을 모델에 보여 주며 다른 상황을 부탁하고,
그래도 같은 말이 오면(대소문자·문장부호만 다른 것도 같은 것으로 본다) 몇 번 더 물어본다.
계속 겹치면 거기서 멈추고 그대로 알려 준다 — 될 때까지 부르면 한도만 깎인다.

**연결이 끊겼다는 말은 작게.**
예전에는 화면 위쪽을 빨갛게 덮었는데, 잠깐 끊긴 것치고는 대화를 가릴 만큼 컸다. 지금은
입력칸 위에 한 줄로 뜨고, 다시 이어지면 조건이 풀리면서 저절로 사라진다. 사람이 닫을
필요가 없는 알림은 사람에게 닫으라고 하지 않는다.

**대화 연결은 화면보다 위에 둔다.**
홈·채팅·단어장처럼 화면이 여러 개가 되면서, 연결을 채팅 화면이 쥐고 있으면 홈에 다녀올
때마다 대화를 다시 받아오고 그 사이에 온 메시지를 놓친다. `Shell` 이 연결을 한 번 잡고
화면만 갈아 끼운다. 안 읽은 개수도 여기서 센다.

**설정이 틀렸다고 앱을 세우지 않는다.**
없으면 앱이 성립하지 않는 값(`AUTH_SECRET`, 두 사람의 정보)만 시작을 막는다.
`CLAUDE_EFFORT` 나 `GEMINI_SAFETY_THRESHOLD` 같은 조절용 설정이 이상하면 경고를 찍고
기본값으로 넘어간다. 쓰지도 않는 provider 의 설정 한 줄 때문에 대화가 멈추는 편이,
기본값으로 도는 것보다 훨씬 나쁘기 때문이다.

**회원가입 없음.**
두 사람은 `.env` 에 고정돼 있다. 로그인은 사람당 패스코드 하나이고, 성공하면 90일짜리 HMAC
서명 토큰을 준다. 세션 저장소도, 비밀번호 재설정 흐름도 없다 — 둘만 쓰는 앱에 필요한 만큼만.

**비밀번호는 바꾼 뒤부터 DB 의 것이 이긴다.**
`.env` 값은 처음 한 번 들어오기 위한 것이고, 앱에서 바꾸면 그때부터 DB 에 있는 scrypt 해시로
확인한다. 바꾸는 순간 그 사람의 토큰 세대를 하나 올려서 예전 토큰을 전부 무효로 만든다 —
바꾸는 이유가 대개 "누가 아는 것 같다"라서, 이미 들어와 있는 쪽이 남으면 바꾼 의미가 없다.
바꾼 기기에는 새 토큰을 바로 돌려줘서 그 기기만 로그인이 유지된다. 세대는 요청마다 DB 를
보지 않고 시작할 때 한 번 읽어 메모리에 둔다(사람이 둘이고 바뀌는 일도 드물다).

## 데이터 모델

대화는 Postgres 에 저장한다. 파일 기반 DB 를 쓰면 배포할 때마다 디스크를 붙여야 하고,
무료 호스팅은 대개 디스크를 주지 않아 재배포마다 대화가 사라진다. 무료 클라우드 Postgres 를
쓰면 호스팅은 아무 데나 골라도 기록이 남는다.

```sql
messages (
  id, sender_id, source_text, source_lang, created_at,
  translation_status   -- pending | done | failed
)

translations (
  message_id, lang, text, notes, model, created_at,
  PRIMARY KEY (message_id, lang)
)

user_settings (
  user_id, native_lang, display_langs   -- 'ko,en' 처럼 콤마로
)
```

스키마는 시작할 때마다 만든다. `CREATE TABLE IF NOT EXISTS` 는 이미 있는 테이블에 컬럼을
더해 주지 않으므로, 나중에 늘어난 컬럼은 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 로
따로 적어 둔다. 먼저 배포된 DB 를 그냥 두면 새 컬럼에 쓰는 순간 터진다.

**번역을 기다리다 만 메시지는 시작할 때 다시 큐에 넣는다.** 무료 호스팅은 자주 잠들고,
번역 도중 서버가 꺼지면 그 메시지는 영원히 "번역하는 중…" 으로 남기 때문이다.

`display_langs` 의 **첫 번째가 주 언어**다. 말풍선에 크게 보이는 번역이 그 언어이고,
나머지는 말풍선을 눌렀을 때 함께 펼쳐진다. 공부 중인 언어를 여기 넣어두면 같은 문장을
여러 언어로 나란히 보게 된다.

번역할 언어는 서버가 정한다: **두 사람이 보고 싶어 하는 언어의 합집합 − 원문 언어**.
그래서 내가 보낸 한국어 메시지도 내가 영어를 켜두었다면 영어 번역이 함께 붙는다.

## WebSocket 프로토콜

클라이언트 → 서버

| 이벤트 | 뜻 |
| --- | --- |
| `send` | 메시지 전송 |
| `typing` | 입력 중 표시 |
| `retranslate` | 이 메시지 번역을 버리고 다시 |
| `read` | 읽음 (현재는 서버가 받기만 한다) |

서버 → 클라이언트

| 이벤트 | 뜻 |
| --- | --- |
| `hello` | 접속 직후 1회. 내 프로필, 상대 프로필, 최근 50개 |
| `message` | 새 메시지 (원문만) |
| `message_updated` | 번역이 붙었거나 상태가 바뀜 |
| `typing` / `presence` | 상대 상태 |
| `error` | 처리 실패 |

연결이 끊기면 클라이언트가 2초 뒤 자동 재연결한다. 단, `hello` 를 한 번도 못 받고 끊겼다면
토큰이 만료된 것으로 보고 로그인 화면으로 돌려보낸다.
